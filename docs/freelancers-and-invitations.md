# Поиск исполнителей и приглашения

Этап 10 добавляет публичный каталог клиентов, которые могут выступать исполнителями, и второй способ создания заказа. Используются прежние v_public_profiles, v_user_ratings, user_skills, project_invitations и таблицы заказов. Новых миграций, ролей и зависимостей нет.

## Поиск и приватность

GET /api/freelancers доступен гостю. Возвращает `{items,total,page,pageSize}` с id, username, именем/фамилией, headline, городом/страной, avatarFileId, навыками, рейтингом исполнителя и числом отзывов. Контакты, credentials, роль, блокировки и внутренние поля не выдаются. В каталог попадают только CLIENT с активным аккаунтом либо истёкшей временной блокировкой; ADMIN и заблокированные скрыты тем же представлением, что и публичный профиль.

| Параметр | Правило |
|---|---|
| search | До 100 символов; буквальная подстрока имени/фамилии в обоих порядках либо username, без учёта регистра |
| skill | Slug одного навыка из справочника; требуется соответствующая связь user_skills |
| minRating | Число от 0 до 5, не более двух знаков после точки; фильтрует рейтинг исполнителя |
| sort | rating (по умолчанию) либо name |
| page / pageSize | 1–10000 / 1–24; по умолчанию 1 / 12 |

Проценты и подчёркивания в поиске не становятся SQL-масками. Значения параметризованы, сортировка берётся из внутреннего whitelist. Рейтинг без отзывов равен null, показан как «Без отзывов» и не соответствует заданному minRating, включая 0. При сортировке по рейтингу такие профили идут последними; далее используются число отзывов, имя и UUID. По имени сортируются фамилия, имя, username и UUID. Фильтры применяются PostgreSQL; total и страница читаются одним SQL-снимком, за последней страницей items пуст, total сохраняется.

Каталог /freelancers сохраняет фильтры/страницу в URL. Карточка ведёт в существующий /users/:id с навыками, портфолио и формой приглашения. Отдельной роли FREELANCER, переключателя аккаунта или выдуманных рейтингов нет: один CLIENT может выступать обеими сторонами разных проектов.

## API приглашений

Все маршруты ниже требуют активной сессии CLIENT и возвращают no-store. Списки имеют `{items,total,page,pageSize}`, команды и отдельное чтение — `{invitation}`.

| Метод и путь /api | Назначение |
|---|---|
| GET /freelancers/:userId/projects | `{projects}`: свои OPEN, доступные для приглашения этого активного клиента |
| POST /projects/:projectId/invitations | Владелец отправляет приглашение, 201 |
| GET /me/invitations | Входящие адресату; box=sent переключает на свои отправленные |
| GET /projects/:projectId/invitations | Приглашения только владельцу проекта |
| GET /invitations/:invitationId | Чтение только отправителю и адресату |
| POST /invitations/:invitationId/accept | Только адресат принимает; пустая команда |
| POST /invitations/:invitationId/decline | Только адресат отклоняет; необязательное `{reason}` |

Создание принимает freelancerId (UUID), message (1–5000), offeredPrice (null/не указан либо положительная десятичная цена до 9999999999.99), offeredDeadlineAt (будущий ISO 8601 с часовым поясом) и необязательный expiresAt (null либо будущий срок ответа). Отсутствующая цена остаётся null, бюджет проекта её не заменяет. Цена хранится NUMERIC и выдаётся строкой с двумя знаками. Стороны, проект и status не подменяются произвольными полями тела; неизвестные поля дают 422. Причина отказа — до 1000 символов, по умолчанию RECIPIENT_DECLINED.

Списки принимают status=PENDING/ACCEPTED/DECLINED/EXPIRED и page/pageSize с теми же границами, что поиск. /me/invitations дополнительно принимает box=incoming/sent и projectId. Идентификаторы отправителя/получателя из query не принимаются. Порядок — created_at DESC, id DESC; total не зависит от наличия строк на текущей странице.

Чужое приглашение, чужой проект и неизвестный UUID возвращают одинаковый 404 соответствующего ресурса. Отправитель не принимает приглашение вместо адресата; ADMIN не подменяет стороны. Приглашать себя нельзя (403 SELF_INVITATION), недоступного адресата — 404 PROFILE_NOT_FOUND, занятый или закрытый свой проект — 409 PROJECT_NOT_OPEN. Второе PENDING той же пары проект/адресат — 409 DUPLICATE_INVITATION; повтор решения — 409 INVITATION_STATE_CONFLICT. Запись имеет лимит 60 команд за 15 минут на IP, общий для браузеров за текущим proxy.

Селектор проектов исключает DRAFT, чужие проекты, активные/завершённые заказы и уже актуальные PENDING тому же адресату. Он возвращает не более 100 строк — существующая квота проектов на клиента. Создание повторяет все проверки под блокировкой: устаревший список не даёт обойти правила. После отказа/истечения можно отправить новое приглашение; источник не возобновляется. PENDING invitation и proposal одной паре могут сосуществовать.

## Состояния, сроки и создание заказа

Отправка создаёт самостоятельный PENDING invitation и уведомление адресату. Заказ ещё не создаётся. Адресат переводит актуальное приглашение в DECLINED либо ACCEPTED. OfferedDeadlineAt и expiresAt проверяются по серверному времени независимо от фонового обработчика. При истечении срока работы причина TERMS_EXPIRED, иначе истечения ответа — TIME_EXPIRED. GET не изменяет БД: показывает expired и canRespond=false для устаревшего PENDING. При создании/решении по проекту устаревшие приглашения фиксируются как EXPIRED, а устаревшие отклики как REJECTED с аудитом/уведомлениями. Попытка принять истёкшее приглашение фиксирует истечение, затем возвращает 409 INVITATION_EXPIRED без заказа. Повтор не дублирует эффекты. Планировщика истечения пока нет.

InvitationService и ProposalService используют общий AssignmentService. Транзакция блокирует обе строки users в порядке UUID, затем project, затем выбранный источник. Повторно проверяются роль/блокировка, адресат, владелец, OPEN, PENDING, сроки и отсутствие активного/завершённого заказа. Блокировка заказчика при принятии даёт 409 COUNTERPARTY_UNAVAILABLE, сохраняя сессию адресата.

В одной транзакции приглашение становится ACCEPTED, создаётся IN_PROGRESS order с invitation_id и null proposal_id, фиксируются стороны, title/description, согласованные цена и начальный/текущий срок, копируются связи project_files в order_files. Проект становится IN_PROGRESS; несовместимые PENDING proposals/invitations закрываются с соответствующей причиной. Записываются ORDER_CREATED, предметный аудит, уведомления о решениях и создании заказа. Единый client pg передаётся всем repositories; вложенных транзакций нет. Уникальные индексы источника и активного/завершённого заказа дополнительно защищают от дублей.

Принятие двух приглашений или приглашения одновременно с откликом имеет одного победителя. Гонки с редактированием, отменой проекта и отказом оставляют согласованное состояние. Ошибка даже последнего события откатывает назначение, файлы, закрытые альтернативы, аудит и уведомления.

Обе стороны видят согласованный снимок в истории приглашений после закрытия публичного проекта. Файлы скачиваются через FileService с Bearer JWT и доступны только участникам; гости и посторонние получают 404. Файлы снимка сохраняются при дальнейших изменениях проекта. Команды выполнения заказа, сдачи и завершения относятся к следующим этапам; платежей нет. Отдельная отмена приглашения отправителем в объём этого этапа не добавлена: актуальность закрывается изменением/отменой проекта, выбором источника или сроком по текущим [переходам](state-transitions.md).

## Проверка и исходные материалы

`node scripts/test-infrastructure.mjs`: 73 unit-теста backend, 84 интеграционных теста PostgreSQL 17 и 6 тестов API-клиента — 163 всего. Сценарии приглашений: поиск/навыки/реальные рейтинги, приватность и скрытие блокированных/ADMIN, стабильная пагинация, права сторон, селектор, дубли, цена null, истечение обоих сроков, отказы, снимок, файлы, аудит/уведомления, повторные решения, конкурентные назначения обоими способами, гонки со сменой условий/отменой/отказом и полный rollback при сбое события. Прежние сценарии откликов сохранены и проходят после выделения общего сервиса. Принятое приглашение ведёт в [карточку заказа](orders.md).

Smoke через frontend proxy проверяет каталог и навык, собственный селектор, запрет принятия отправителем, создание второго заказа через invitation и сохранность обоих заказов после реальной замены контейнеров. Автоматические тесты и браузерный сценарий работают в отдельных временных Compose-проектах. Неизменяемые аудит и события не очищаются обходом триггеров: тестовые volumes удаляются целиком, рабочая база не используется.

В браузере проверены поиск и URL-фильтры, отсутствие нерейтингового профиля при minRating, выбор своего проекта, отправка, входящие/отправленные, отказ с причиной, принятие, снимок и скачивание файла, reload и мобильная ширина 390 px. Отдельно проверено автоматическое обновление обоих списков после отмены проекта: без reload отклик становится отклонённым, приглашение закрытым, недоступные действия исчезают. Фиктивные участники и заказы удаляются вместе с временным окружением.

Изучены ООП FreelancerSearchViewModel.cs, UserSearchRepository.cs и AcceptInviteAsync/DeclineInviteAsync из UserProfileRepository.cs; сопоставлены текущие 08_rest_api.md и согласованные переходы. Сохранены поиск, выбор свободного своего проекта и ответ адресата. Идентификатор notification как источник заказа, EF/WPF, роли CUSTOMER/FREELANCER и прямое создание заказа отправителем не переносятся.
