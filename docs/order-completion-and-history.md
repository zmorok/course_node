# Завершение, отмена и события заказа

Этап 13 завершает основной workflow заказа. Приёмка последней версии уже реализована в [этапе 12](submissions-and-deadlines.md): ACCEPTED version, COMPLETED order/project и ORDER_COMPLETED сохраняются одной транзакцией. Проект исчезает из OPEN-каталога. Новая реализация добавляет отмену любой стороной, повторное открытие проекта и приватную ленту событий. Миграций и новых зависимостей нет.

## Отмена и новая договорённость

POST /api/orders/:orderId/cancel принимает только `{reason}`: 1–1000 символов, без управляющих символов, пробелы по краям удаляются. Команда требует активной сессии CLIENT, фактического участия и IN_PROGRESS/SUBMITTED/REVISION_REQUESTED. Автор, время и статусы определяются сервером. Гость — 401, ADMIN/блокированный — 403, чужой/неизвестный заказ — одинаковый 404, повторная отмена и терминальный статус — 409. Ответ: 200 `{orderId}`, no-store. Произвольных PATCH/DELETE заказа нет.

Под блокировками users по UUID → project → order повторно проверяются текущий участник и матрица. В одной транзакции pending deadline становится EXPIRED с ORDER_CANCELLED, нерассмотренная SUBMITTED version — CANCELLED, order — CANCELLED с cancelled_by/at/reason, project — OPEN. Рассмотренные версии, содержимое результата, файлы, соглашение и принятый источник не меняются. Заблокированная вторая сторона не лишает активного участника его допустимого права отмены.

Создаются ORDER_CANCELLED, audit и уведомление второй стороне. Ошибка события откатывает всю отмену, включая статус проекта, версию и pending. При гонке приёмки и отмены один запрос фиксирует согласованный терминальный результат; другой получает конфликт. Две отмены также имеют одного победителя. БД дополнительно сохраняет уникальность активного/завершённого заказа проекта.

OPEN снова доступен для откликов/приглашений. Новый принятый источник создаёт новый order с новым UUID, сторонами и снимком. Старый ACCEPTED источник не используется повторно, старые результаты доступны только его сторонам. Изменение задания или назначение другого исполнителя не переписывает старую историю. Проектные файлы подчиняются обычной политике OPEN-проекта; приватные submission_files не становятся публичными после открытия проекта.

## Лента событий

GET /api/orders/:orderId/events доступен только действующему CLIENT-участнику, включая COMPLETED/CANCELLED. Query: page 1–10000 (1), pageSize 1–24 (12); неизвестные параметры дают 422. Ответ `{items,total,page,pageSize}`, no-store. Count/страница читаются одним SQL-снимком, порядок created_at DESC/id DESC, total сохраняется за последней страницей.

Событие содержит id/type/date, ссылки на version/request, минимальное имя автора и его сторону либо actor=null для системы. Метаданные ограничены version/reason/previousDeadlineAt/proposedDeadlineAt. Контактов, credentials и storage keys нет. Новые события получают clock_timestamp после блокировок; чтение ничего не изменяет. История order_events защищена прежними триггерами от UPDATE/DELETE/TRUNCATE.

Карточка показывает ленту создания, версий, доработок, сроков, приёмки и отмены. Действия после успешных команд обновляют её вместе с данными заказа. Отмена требует формы с причиной и отдельного подтверждения; есть возврат к работе, ошибки и повтор обновления. Соглашения в принятых источниках показывают фактический текущий статус заказа. Активные/история и режимы списка используют прежний раздел заказов.

## Проверка

`node scripts/test-infrastructure.mjs`: 77 unit-тестов, 100 интеграционных тестов PostgreSQL 17 и 6 тестов API-клиента — 183 всего. Новые сценарии: оба участника/оба источника/все активные состояния, роли и блокировки, гонки приёмки/отмены, rollback события, сохранение старых файлов/снимка при новом назначении и приватная пагинация событий. Приёмка и завершённый каталог продолжают проверяться реальными командами.

Smoke отменяет заказ, проверяет OPEN, назначает другого исполнителя, читает приватную старую ленту и проверяет сохранность отмены/нового заказа после замены контейнеров. Браузерная проверка проводится в отдельной временной базе с обеими сторонами, подтверждением причины, reload, повторным открытием, новым назначением, историей и ширинами 390/1280 px. Тестовые данные не попадают в рабочие volumes.

Изучены старые DeleteSelectedAsync/SaveAsync из OrdersViewModel.cs и текущие 08_rest_api.md/[переходы](state-transitions.md). Физическое удаление заказа и произвольное редактирование status из WPF заменены отменой с историей, явной приёмкой и событиями. Платежей и отдельной архивной таблицы нет.
