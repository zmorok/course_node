# Жалобы клиента и предупреждения

Этап 15 использует существующие complaints, complaint_files, moderation_actions, warnings, v_user_sanctions, audit_logs и notifications. Новых миграций или зависимостей нет. Из ООП изучены ComplaintsViewModel.cs, UserComplaintsRepository.cs и IssueWarningAsync из ComplaintsModerationViewModel.cs. Сохранены выбор заказа/контрагента, поданные обращения и доказательства. По [согласованной модели](domain-model.md) прежние редактирование/удаление жалобы, архивная таблица, передаваемые клиентом стороны и Base64 заменены неизменяемой подачей и FileService.

## Жалобы

| Метод и путь после /api | Назначение |
| --- | --- |
| POST /orders/:orderId/complaints | Подать жалобу; 201 с complaint |
| GET /orders/:orderId/complaints | Только собственная жалоба, canComplain и ID второй стороны |
| GET /me/complaints | Свои поданные жалобы с фильтрами и пагинацией |
| GET /me/complaints/:complaintId | Собственная жалоба и итог рассмотрения |

Подача требует активной сессии CLIENT и участия в COMPLETED/CANCELLED заказе. reason — 1–80 символов, description — 1–5000; пробелы по краям удаляются, управляющие символы запрещены. Необязательный fileIds содержит до 8 различных UUID своих свободных файлов. Роль, время, NEW, reporter и target определяет сервер по исходному заказу. Неизвестные поля/параметры отклоняются. Отзыв не является условием подачи; повторное назначение проекта не меняет адресата старой жалобы.

Один reporter имеет максимум одну жалобу по order независимо от её исхода. Нет клиентских команд редактирования, удаления или добавления доказательств после подачи. Гость — 401, ADMIN/действующая блокировка — 403, чужой/неизвестный заказ или жалоба — одинаковый 404, активный заказ/дубликат — 409, неверный ввод — 422. Создание ограничено 30 запросами за 15 минут на IP.

Транзакция блокирует users по UUID → project → order → files. Под блокировками повторно проверяются текущая роль/блокировка, участие, терминальный статус, уникальность и владение свободными файлами. INSERT жалобы, связи доказательств и COMPLAINT_CREATED в audit_logs фиксируются вместе; сбой откатывает всё. Конкурентные подачи одного автора имеют одного победителя, встречные жалобы — разные UUID. Рабочие статусы заказа/проекта не меняются.

Список принимает mode=customer/freelancer (по умолчанию customer), status=NEW/IN_REVIEW/RESOLVED/REJECTED, page=1–10000 и pageSize=1–24 (1/12 по умолчанию). Необязательный direction допускает только submitted; received и подмена reporter/target отклоняются. Сортировка created_at DESC, id DESC стабильна, total сохраняется за последней страницей. Ответы no-store. Клиент читает только свои обращения, имена адресата, заголовок исходного заказа, доказательства, даты и resolutionNote. Жалоба второй стороны и её текст ему не раскрываются.

Доказательства загружаются обычным POST /files через Multer/FileService в uploads_data. В БД хранятся только метаданные и связи. Для привязки нельзя использовать чужую, удалённую, уже занятую или неизвестную загрузку. Reporter читает свои файлы с Bearer JWT, другая сторона/гость/новый исполнитель получают 404. complaint_files уже учитывается общей проверкой FILE_IN_USE: доказательства нельзя удалить, даже когда проект снова открыт. Контекстный доступ ADMIN к чужим доказательствам реализован вместе с [административной карточкой](administration.md) этапа 16.

## Предупреждения

GET /api/me/warnings доступен только активному CLIENT и читает его собственный v_user_sanctions. Фильтр type=WARNING/TEMPORARY_BLOCK/PERMANENT_BLOCK необязателен; пагинация имеет те же границы. Порядок created_at DESC, moderation_action_id DESC, total устойчив на пустой странице. Показываются текст, тип, дата, срок, минимальное имя администратора и complaintId при наличии. Текст чужой жалобы, reporter и доказательства не выдаются. Прошлые записи и истёкшие сроки сохраняются. Клиентских команд создания, правки, удаления или отметки прочтения нет.

POST /api/admin/users/:userId/warnings выдаёт отдельное предупреждение только активному ADMIN действующему или заблокированному CLIENT. Body содержит только message (1–5000) и необязательный expiresAt (null либо ISO с часовым поясом, строго в будущем). Автор/target/state/action/complaintId из body не принимаются. После блокировки admin и target по UUID права и срок проверяются заново. WARNING moderation action, связанная warnings, WARNING_ISSUED audit и MODERATION_ACTION notification создаются одной транзакцией. Лимит — 60 запросов за 15 минут на IP, ответ 201 с warning.id/actionId и no-store. На ADMIN/неизвестного адресата возвращается 404.

Связь предупреждения с жалобой хранится через moderation_actions.complaint_id; WarningRepository.create принимает этот контекст для общей транзакции решения. Клиентский список уже показывает такие предупреждения. Публичная выдача отдельного предупреждения не закрывает жалобу и не принимает произвольный complaintId. Claim, решения с санкциями обеим сторонам, block/unblock и административный интерфейс реализованы в [этапе 16](administration.md); связанное предупреждение создаётся атомарно с решением, по [переходам](state-transitions.md).

## Интерфейс и проверка

В заказе добавлена форма с фиксированным получателем, причиной, описанием и необязательными доказательствами. Новые загрузки при отмене остаются в личных свободных файлах. Серверная ошибка сохраняет черновик; успешная отправка показывает сохранённую запись без формы повторной подачи. Раздел «Жалобы» содержит два режима, фильтр статуса, пагинацию, приватную карточку и итог. Раздел «Предупреждения» отдельно показывает историю только для чтения с фильтром типа. Есть загрузка, пустые списки, ошибки и повторные запросы; при выходе закрытые данные очищаются общим механизмом сессии.

`node scripts/test-infrastructure.mjs`: 89 unit-тестов backend, 133 интеграционных тестов PostgreSQL 17 и 6 тестов API-клиента — 228 всего. Новые сценарии проверяют обе стороны, оба источника и терминальных статуса, все активные статусы, роли/блокировки, whitelist, уникальность/гонки, неизменяемость, приватные доказательства и их сохранение при новом назначении, откат аудита, фильтры/пагинацию, вывод решения, связь предупреждения с жалобой, отдельную выдачу только ADMIN, read-only клиента и повторную проверку полномочий после ожидания блокировки.

Smoke выполняет подачу с файлом и предупреждение через frontend proxy, проверяет дубликаты/приватность и сохранность записей/байтов после замены контейнеров. В браузере на отдельной временной базе проверены обе формы одного CLIENT, загрузка TXT, серверная ошибка с сохранением описания, статусы/итог из административных фикстур, оба режима списка и фильтр предупреждений. Ширины 390/1280 px не дают горизонтального переполнения. Временное окружение и файлы проверки удаляются целиком, рабочая БД не очищается.
# Редактирование новых жалоб — этап 23

До начала рассмотрения автор может изменить причину, описание и доказательства через `PUT /api/me/complaints/:id` либо удалить жалобу через `DELETE` того же адреса. После перехода из NEW обе команды возвращают 409. Чужое обращение не раскрывается. Решение проверяется после блокировки участников и самой жалобы; конкурентное взятие в работу не позволяет изменить уже рассматриваемые данные. Снятые файлы удаляются через общий жизненный цикл; изменения и удаление остаются в аудите.
