# Профиль и навыки Workify

Этап 06 добавляет просмотр и редактирование своих данных, выбор навыков из справочника и публичную карточку клиента. Используются существующие users/profiles/skills/user_skills и v_public_profiles; на этапе 06 схема не менялась. [Аватар, файлы и портфолио](files-and-portfolio.md) реализованы на этапе 07.

## API и доступ

| Метод и путь | Доступ | Ответ |
|---|---|---|
| GET /api/me/profile | Действующая сессия CLIENT/ADMIN | `{profile}` со своими контактами и навыками |
| PATCH /api/me/profile | Действующая сессия CLIENT/ADMIN | Сохранённый `{profile}` |
| PUT /api/me/skills | Действующая сессия CLIENT | `{profile}` с заменённым набором навыков |
| GET /api/skills | Гость и пользователь | `{skills: [{id, slug, name}]}` |
| GET /api/users/:userId | Гость и пользователь | `{profile}` с публичными полями активного CLIENT |

Защищённые запросы используют Bearer JWT и проверку актуальной сессии, роли и блокировки из этапа 05. Идентификатор владельца всегда берётся из request.user.id; пользователь не передаёт его в body. ADMIN редактирует свои личные данные, но не назначает себе навыки и не публикуется как клиент. Блокировка закрывает обычные защищённые операции; изменяющий сервис дополнительно проверяет статус после блокировки строки users.

Публичный ответ содержит id, username, имя/фамилию, специализацию, описание, город/страну, навыки, avatarFileId и два раздельных рейтинга/числа отзывов. Email, телефон, роль, поля блокировки, пароль, hash и sessions отсутствуют. Рейтинги читаются из существующего view, а не записываются пользователем; без отзывов рейтинг null и количество 0. AvatarFileId также возвращается в своём профиле; изображение выдаёт GET /api/files/:fileId после проверки доступа.

Несуществующий, заблокированный или административный публичный профиль возвращает одинаковый 404 PROFILE_NOT_FOUND. Истёкшая временная блокировка не скрывает клиента. UUID параметра валидируется до SQL. Все ответы имеют Cache-Control: no-store; ошибки используют общий JSON envelope с requestId.

## PATCH и проверка данных

PATCH меняет только переданные поля. Пропущенные значения сохраняются; пустой объект или один currentPassword без изменений отклоняются с 422. Разрешённые поля:

| Поле | Ограничение / очистка |
|---|---|
| firstName, lastName | Строки 1–100, пробелы по краям удаляются |
| username | 3–40, латиница/цифры/подчёркивание; уникальность без учёта регистра |
| email | До 254, формат как при регистрации; уникальность без учёта регистра |
| headline | До 200; пустая строка очищает специализацию |
| description | До 5000; переносы строк разрешены, исходный HTML не исполняется React |
| phone | До 30; цифры, начальный +, пробелы, скобки, точка и дефис; пустое/null очищает |
| city, country | До 100; пустое/null очищает |
| currentPassword | Только подтверждение смены email; 1–128, пробелы сохраняются |

Для однострочных полей запрещены управляющие символы; описание разрешает табуляцию и переносы, но отклоняет NUL и прочие управляющие символы. Все неизвестные поля отклоняются. Через этот API нельзя менять id/userId/user_id, role, status, блокировку, рейтинг, дату создания, password/password_hash или skills. Навыки изменяются отдельной командой.

Смена email на другой адрес требует текущий пароль: отсутствие даёт 422 VALIDATION_ERROR с body.currentPassword, неправильный пароль — 403 INVALID_CURRENT_PASSWORD. Изменение только регистра того же адреса не меняет его идентичность и повторный пароль не требует. Password hash никогда не меняется и не возвращается. После сохранения вход работает с новым адресом; старый перестаёт подходить. Сессии сохраняются, поскольку привязаны к UUID пользователя. Письма подтверждения и смена самого пароля этим этапом не реализуются.

Формат email/username переиспользуется из validators/auth.js. Уникальность обеспечивается индексами БД, включая гонки: конфликт даёт 409 PROFILE_CONFLICT без имени constraint или деталей драйвера. Изменение users и profiles выполняется в одной транзакции; отказ проверки/конфликт не сохраняет остальные поля этого запроса.

## Сохранение навыков и конкурирующие изменения

PUT /me/skills принимает только `{skillIds: [...]}`: до 50 уникальных UUID существующего справочника. Пустой список очищает набор. Неподходящий тип, повтор, неизвестный UUID, превышение лимита или дополнительные поля дают 422. Клиент не создаёт новые навыки строками.

Сервис блокирует свою строку users, повторно проверяет CLIENT/активность, читает выбранные skills с FOR SHARE, затем удаляет прежние связи и вставляет новый набор. Проверка, полная замена и обновление времени профиля входят в одну транзакцию. Неизвестный навык не удаляет предыдущий набор. Два PUT одного аккаунта сериализуются: остаётся один целый набор, без смешивания списков. PATCH использует ту же блокировку; независимые частичные изменения не сбрасывают друг друга. Время обновления обслуживается существующим trigger profiles.

SQL находится в profile.repository.js. Названия изменяемых столбцов берутся из фиксированных внутренних maps; значения и UUID передаются через параметры pg. Controllers только переводят HTTP в вызов сервиса и JSON, сервис не зависит от req/res.

PATCH профиля и PUT навыков делят лимит 30 запросов за 15 минут на IP. Счётчик находится в памяти одного backend; особенности IP за текущим frontend proxy совпадают с [настройками авторизации](auth.md#конфигурация-и-первый-admin). Превышение даёт общий JSON 429 и Retry-After.

## React

`/me/profile` открывается по ссылке «Мой профиль» в аккаунте/шапке. Гость видит форму входа, после входа открывается профиль по тому же адресу. Поля предварительно заполнены; профиль и навыки имеют независимые кнопки сохранения/отмены и сообщения результата. Кнопки сохранения выключены без изменений и во время другого сохранения. Ошибка не стирает введённые данные.

Навыки имеют поиск по названию/slug, checkbox-выбор и счётчик. Фильтрация не сбрасывает скрытые выбранные навыки; пустой результат объясняется текстом. Смена email показывает поле текущего пароля. Сохранённые имя/username/email обновляются в карточке аккаунта и после reload. Боковая карточка показывает сохранённые данные; публичный профиль открывается в новой вкладке, сохраняя несохранённую форму.

`/users/:userId` показывает публичную карточку без контактов, описание, навыки и раздельные рейтинги. Неизвестный/скрытый профиль имеет понятное состояние ошибки. На узких экранах поля и колонки складываются; исправленная компактная регистрация этапа 05 сохраняется.

API-клиент при истечении JWT обновляет его и повторяет запрос один раз. Ошибка бизнес-проверки после успешного refresh (например, неверный текущий пароль) сохраняет сессию и показывается в форме. Повторный 401 или блокировка сбрасывают локальную сессию; бесконечного цикла повторов нет.

## Проверки и исходные материалы

```powershell
node scripts/test-infrastructure.mjs
```

Общий runner запускает 57 unit-тестов backend, 41 интеграционный тест PostgreSQL и 8 frontend-тестов на Node.js 24 в отдельных контейнерах. Тестовые исходники монтируются read-only и не входят в runtime image. Дополнительно проверяются реальные HTTP-запросы через frontend proxy, сохранение профиля/навыков после пересоздания контейнера и прежние проверки инфраструктуры. Все автоматические данные используют одноразовую базу.

Проверяются whitelist, типы/лимиты/управляющие символы, частичный PATCH, очистка полей, владение, CLIENT/ADMIN/блокировки/отзыв сессии, смена email и login, уникальность с откатом остальных изменений, приватность публичного ответа, сохранение/очистка/ошибки навыков, конкурентные PUT/PATCH. Тесты API-клиента проверяют успешный refresh и однократный повтор, неверный пароль после refresh, блокировку и повторный 401.

В браузере проверены вход в защищённую страницу, заполнение/сохранение, выбор трёх навыков, поиск, отмена выбора, reload, обновлённая карточка аккаунта и чтение публичного профиля после выхода. При ширине 390 проверено отсутствие горизонтальной прокрутки; временный viewport возвращается к обычному размеру. Собственная браузерная тестовая запись удаляется после проверки.

Из исторической базы прочитаны OOP `FreelanceApp/Windows/ViewModels/User/ProfileViewModel.cs` и `DAL/Repository/UserRepositories/UserProfileRepository.cs`: сохранены редактирование своих данных, email и контактов. Уведомления/приглашения из старого ProfileViewModel не переносятся в этот этап; SHA-512, bytea-фото и непосредственный desktop-доступ к БД не используются. Сопоставлены текущие `docs/02_roles_and_interface_modes.md`, `08_rest_api.md` из Workify_STSR_Project_Specification_v4 и действующая матрица прав. Поля, приватность и источник рейтингов взяты из текущих users/profiles/v_public_profiles, а не из старой desktop-модели.

[Отзывы этапа 14](reviews.md) публикуются отдельно в контексте заказчика и исполнителя; видимые оценки рассчитываются в PostgreSQL и используются профилем и каталогом исполнителей.

# Дополнение этапа 21

В профиле доступны необязательные `middleName` и `gender` (`Male`, `Female`, `Other` или пустое значение). Публичный профиль показывает их и `lastOnlineAt`; контакты остаются приватными. Присутствие обновляется при входе и авторизованных запросах с ограничением частоты записи до одного раза в минуту.

`POST /api/me/password` принимает `currentPassword` и `newPassword` (12–128 символов). Проверка текущего пароля, запись нового хеша, отзыв всех сессий и аудит выполняются в одной транзакции. После успеха интерфейс предлагает войти заново. Пароли и их хеши не записываются в аудит.
