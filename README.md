# Workify

Курсовой проект «Веб-приложение для управления проектами и заказами на IT-фриланс-площадке».

Workify объединяет публикацию IT-проектов, подбор исполнителя через отклик или приглашение, выполнение заказа, сдачу версий результата, согласование сроков, отзывы и административное рассмотрение жалоб.

## Состояние проекта

Этапы 01–27 завершены: реализованы предметная модель, PostgreSQL 17, Docker Compose, слоистый backend, авторизация, профиль, файлы, портфолио, проекты, отклики, приглашения, заказы, версии результата, доработки, приёмка, сроки, отмена, история событий, двусторонние отзывы, подача жалоб, предупреждения, административная панель, централизованный аудит и центр уведомлений. Оба способа согласования создают заказ транзакционно; отменённый заказ сохраняется, а проект открывается для новой договорённости. Отзывы и рейтинги разделены по режимам заказчика и исполнителя.

- Основная ветка – `main`; завершённые этапы отмечаются аннотированными тегами `stage-01-complete` – `stage-27-complete`, их ветки сохраняются.
- Исходный релиз курсового – `stsr-course-release` (1.0.0); релиз доработок – `stsr-wpf-parity-release`, версия приложения 1.1.0. Основной workflow заказа проверен до взаимных отзывов, рассмотрения жалобы и чтения предупреждения.

Этапы 21–27 дополнили профиль отчеством, полом, сменой пароля и присутствием; портфолио – опытом и навыками работ; отзывы – изображениями GIF/BMP/PNG/JPEG/WebP. Добавлены изменение новых жалоб, управление аккаунтами и ролями в админке, импорт/экспорт аудита, RU/EN и две темы.

## Запуск приложения

Нужны работающий Docker Engine с Compose и локальный Node.js 24 с npm. React собирается на компьютере, а приложение обслуживают контейнеры Nginx, Node.js 24 и PostgreSQL 17.

```powershell
node scripts/setup-env.mjs
npm --prefix frontend ci
npm --prefix frontend run build
docker compose up --build -d --wait --remove-orphans
```

Скрипт создаёт локальный `.env` с независимыми случайными паролями владельца БД и приложения, а также JWT secret, не выводя их. В старый `.env` дописываются только отсутствующие `APP_DB_PASSWORD` и `AUTH_JWT_SECRET`; остальные настройки сохраняются. Перед запуском backend автоматически применяются миграции и права отдельной роли `workify_runtime` без привилегий суперпользователя.

`--remove-orphans` также удаляет старый контейнер `frontend` при переходе на новую схему. Данные приложения находятся в отдельных volumes.

- [Приложение](http://localhost:5173).
- [Каталог открытых проектов](http://localhost:5173/projects).
- [Поиск исполнителей](http://localhost:5173/freelancers).
- [Свои заказы](http://localhost:5173/me/orders) – после входа как CLIENT.
- [Проверка backend и БД](http://localhost:3000/api/health).
- [Проверка API через Nginx](http://localhost:5173/api/health).

Остановка – `docker compose down`. Данные PostgreSQL и файлы сохраняются в volumes `postgres_data` и `uploads_data`. Порты и настройки меняются через `.env`; в Git хранится только [.env.example](.env.example).

## Фронтенд и обратный прокси

```text
приложение/
  frontend/          исходники React, зависимости и настройки Vite
  proxy/
    nginx.conf       конфигурация Nginx
    bundle/          готовая сборка React, создаётся командой build
```

Vite записывает сборку сразу в `proxy/bundle`. В контейнер `proxy` на базе `nginx:alpine` монтируются только `proxy/nginx.conf` и `proxy/bundle`, оба пути доступны Nginx только для чтения. Каталог `frontend` остаётся обычным локальным проектом; его исходники и `node_modules` контейнеру Nginx не нужны. Сгенерированный `bundle` исключён из Git.

```text
Браузер -> localhost:5173 -> proxy:8080
                            /         -> файлы из proxy/bundle
                            /api/*    -> backend:3000 -> postgres:5432
```

После изменения исходников на Windows выполните из папки `приложение`:

```powershell
npm --prefix frontend run build
```

После завершения сборки обновите страницу в браузере. Nginx сразу видит новые файлы через bind mount; пересоздавать контейнер или перезагружать Nginx не требуется. Для автоматической пересборки при сохранении исходников:

```powershell
npm --prefix frontend run build:watch
```

Из самой папки `frontend` используются обычные `npm run build` и `npm run build:watch`. Nginx требует готовый `bundle/index.html` для успешной проверки состояния. В изолированных инфраструктурных тестах `WORKIFY_BUNDLE_DIR` задаёт отдельный каталог сборки и не затрагивает рабочий `proxy/bundle`.

Nginx сохраняет префикс `/api` и параметры запросов, отдаёт `index.html` для маршрутов SPA, возвращает 404 для отсутствующих файлов и JSON с кодом 502 при недоступности backend. Лимит HTTP-запроса 11 МиБ позволяет передавать файлы до 10 МиБ с multipart-заголовками; предметные ограничения проверяет backend. Docker DNS позволяет Nginx найти новый адрес backend после пересоздания его контейнера. Backend доверяет одному прокси; Nginx перезаписывает заголовки адреса клиента и протокола.

Сейчас используется HTTP. Для будущей схемы `клиент -> HTTPS -> Nginx -> HTTP -> backend` сертификаты и HTTPS-listener добавляются в `proxy/nginx.conf`, а `AUTH_COOKIE_SECURE` устанавливается в `true`. Заголовок `X-Forwarded-Proto` уже передаёт backend протокол клиентского соединения. Порт backend по-прежнему опубликован только на localhost для локальной разработки и диагностики.

Smoke-проверка сборки, API, сохранности volumes и восстановления после остановки сервисов в отдельном тестовом проекте:

```powershell
node scripts/test-infrastructure.mjs
```

## Проверки и демонстрация

Основной набор: 94 backend unit, 142 integration и 16 frontend unit (252 теста), затем HTTP E2E через Nginx, обновление bind mount без перезапуска прокси, замена контейнеров и восстановление сервисов. Проверки запускаются в отдельных временных базах, volumes и каталоге сборки. Перед запуском нужны зависимости фронтенда: `npm --prefix frontend ci`.

Отдельные браузерные проверки SPA запускаются из `frontend`: `npm ci`, `npx playwright install chromium`, `npm run test:browser`. 32 сценария проверяют клиентские и административные экраны на ширинах 320–1920 px, действия по ролям, переходы без загрузки документа, историю, фильтры, формы, язык, тему и неизвестные адреса. API в этих сценариях подменяется тестовыми ответами; рабочая БД не используется. Интерфейс обновляет разделы, язык и тему без перезагрузки страницы.

Первый ADMIN создаётся операторской командой после обычной регистрации.

## База данных

Схема `workify` содержит 32 таблицы: 29 предметных и вспомогательных, две таблицы авторизации и журнал миграций; также созданы пять представлений и справочные категории/навыки. Для файлов в БД хранятся только метаданные, а история заказов определяется статусами в `orders`.

Применение миграций к отдельной существующей базе с подключением через стандартные настройки `psql`:

```powershell
psql -X -v ON_ERROR_STOP=1 -d workify -f database/migrate.sql
```

В `database/migrate.sql` перечислены имена SQL-файлов и вызовы общего `apply-migration.sql`. Обработчик применяет только отсутствующие в журнале версии; после них загружаются справочные категории и навыки из `seeds/reference_data.sql`. Новая миграция добавляется одной строкой.

## Согласованный стек и границы

- JavaScript, React, Nginx, Node.js + Express, PostgreSQL 17, Docker Compose.
- Backend: `routes -> controllers -> services -> repositories/DAO -> PostgreSQL`; SQL выполняется через `pg` в repositories/DAO, бизнес-правила находятся в services.
- Системные роли: `CLIENT`, `ADMIN`. Заказчик и исполнитель – режимы одного `CLIENT`, определяемые его участием в конкретном проекте или заказе.
- Multer и общий FileService; файлы хранятся в Docker volume `uploads_data`, PostgreSQL хранит метаданные и связи.
- Nginx раздаёт локальную React-сборку и проксирует API. Платежи оставлены для диплома; Redis, MinIO и микросервисы в объём курсового не входят.

## Стиль кода бэкенда

Исходники и тесты бэкенда оформлены единообразно. Настройки Prettier находятся в `backend/.prettierrc.json`, версия форматтера закреплена в devDependencies. Используются отступы в два пробела, одинарные кавычки и ориентир ширины строки 100 символов. Условия и циклы записываются с фигурными скобками, переменные объявляются отдельно, логические блоки разделяются пустыми строками.

Команды форматирования выполняются из папки `приложение` с Node.js 24:

```powershell
npm --prefix backend ci
npm --prefix backend run format:check
npm --prefix backend run format
```

`format:check` проверяет оформление, `format` исправляет его. При изменении структуры кода дополнительно запускается существующий набор проверок: `node scripts/test-infrastructure.mjs`. Он использует отдельные временные контейнеры, БД, volumes и сборку фронтенда.

## Стиль кода фронтенда

Фронтенд использует тот же базовый стиль JavaScript. JSX-разметка и CSS раскрыты в читаемые блоки; короткие элементы остаются компактными. В `src/styles.css` выделены группы правил по разделам интерфейса, а в `src/tokens.css` – палитра, семантические цвета и размеры. Порядок CSS-правил сохраняется, чтобы оформление экранов оставалось прежним.

Настройки находятся в `frontend/.prettierrc.json`. Команды из папки `приложение`:

```powershell
npm --prefix frontend ci
npm --prefix frontend run format:check
npm --prefix frontend run format
npm --prefix frontend test
npm --prefix frontend run test:browser
```

Браузерные сценарии проверяют навигацию, формы, роли, темы, язык и адаптивную вёрстку. Перед первым запуском установите Chromium из папки `frontend`: `npx playwright install chromium`.

## Работа с Git

Каждый этап выполняется в отдельной ветке от `main`. После проверок он вливается через `git merge --no-ff` и отмечается аннотированным тегом `stage-NN-complete`. Основной журнал изменений – история Git. После завершения этапов текущие исправления по согласованию с владельцем выполняются непосредственно в `main`, отдельными содержательными коммитами после проверок.

Содержательные коммиты имеют один префикс слоя: `UI:`, `Back:`, `DB:`, `Infra:`, `Test:` или `Docs:` и понятное описание на русском языке. Секреты, `.env`, зависимости, результаты сборки и загруженные пользователями файлы исключены из Git. Безопасные `.env.example` допускаются.
