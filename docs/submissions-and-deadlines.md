# Версии результатов, доработки и согласование сроков

Этап 12 расширяет [раздел заказов](orders.md) командами сдачи, рассмотрения результата и изменения срока. Используются существующие order_submissions, submission_files, order_deadline_requests, order_events, audit_logs и notifications. Новых миграций, зависимостей и системных ролей нет; файлы остаются в Docker volume и выдаются FileService.

## HTTP API

Все маршруты требуют активной сессии CLIENT, участия в заказе и возвращают Cache-Control: no-store. Сторона берётся из текущего аккаунта и заказа. ADMIN не выполняет действия за участника. Неверный UUID, неизвестное поле или непустой query команды дают 422. Неизвестный/чужой заказ — одинаковый 404 ORDER_NOT_FOUND.

| Метод и путь /api/orders/:orderId | Действие / тело |
|---|---|
| GET /submissions | Приватная история версий |
| POST /submissions | Исполнитель: `{comment,links?,fileIds?}`, 201 `{submissionId,version}` |
| POST /submissions/:submissionId/revision | Заказчик: `{comment}`, 200 `{submissionId}` |
| POST /submissions/:submissionId/accept | Заказчик: `{comment?}`, 200 `{submissionId}` |
| GET /deadline-requests | Приватная история запросов срока |
| POST /deadline-requests | Исполнитель: `{proposedDeadlineAt,reason}`, 201 `{requestId}` |
| POST /deadline-requests/:requestId/approve | Заказчик: `{reason?}`, 200 `{requestId}` |
| POST /deadline-requests/:requestId/reject | Заказчик: `{reason}`, 200 `{requestId}` |

GET-истории принимают только page=1–10000 (1), pageSize=1–24 (12), возвращают `{items,total,page,pageSize}`. Версии упорядочены по version DESC, запросы — created_at DESC/id DESC. Count и страница читаются одним SQL-снимком; за последней страницей total сохраняется. Вложенная чужая версия/заявка не находится, даже если UUID существует в другом заказе. PUT/PATCH/DELETE содержимого версий, произвольного status/сторон/дедлайна и прямого POST /orders нет.

Комментарий результата/доработки — 1–5000 символов, причина запроса/отказа срока — 1–1000; пробелы по краям удаляются, управляющие символы запрещены. Необязательные comment при приёмке и reason при одобрении могут отсутствовать или быть null. Links — до 5 полных HTTP(S) ссылок до 2048 символов, без credentials и пробельных/управляющих символов. FileIds — до 8 различных UUID. Для сдачи нужен непустой комментарий и хотя бы один файл или ссылка. Предлагаемая дата — ISO 8601 с часовым поясом; сервер нормализует её и проверяет будущее время/отличие от текущего срока. Запись ограничена 60 командами за 15 минут на IP.

## Неизменяемые версии и решения

Исполнитель сдаёт только IN_PROGRESS или REVISION_REQUESTED. Под блокировкой заказа сервер назначает max(version)+1, создаёт SUBMITTED version, связи файлов и переводит заказ в SUBMITTED. Цена, исходное задание и первоначальный срок не меняются. Новая сдача из SUBMITTED запрещена. Ранее рассмотренные версии сохраняют содержимое, статус, автора и решение; новая сдача после замечаний создаёт следующую запись.

Файлы должны принадлежать исполнителю и быть свободными, не удалёнными. FileService блокирует UUID в стабильном порядке и проверяет все существующие связи. Занятый файл нельзя повторно привязать к другой версии: нужно загрузить отдельную копию либо использовать ссылку. Файлы версии доступны только участникам заказа и остаются доступны после доработки/завершения. Гость и посторонний получают 404; generic DELETE не удаляет используемые байты. Для результата нет публичных image URL, storage key или раздачи каталога uploads.

Рассмотреть можно только конкретную последнюю SUBMITTED-версию. Доработка сохраняет reviewed_by/at и обязательный комментарий, переводит версию и заказ в REVISION_REQUESTED. Приёмка сохраняет ACCEPTED и решение, атомарно переводит order/project в COMPLETED с completed_at. Приёмка реализована здесь, поскольку входит в сценарий этапа 12 и не должна оставлять принятую версию в активном заказе. Завершённый проект не попадает в OPEN-каталог; платежей нет. Повторное/конкурентное решение даёт конфликт без повторных эффектов. Отмена заказа, повторное открытие проекта и общая лента событий остаются этапом 13.

## Запросы срока и просрочка

Запрос доступен исполнителю в IN_PROGRESS/REVISION_REQUESTED. Он сохраняет previous_deadline_at, proposed_deadline_at и причину, но не меняет deadline_at заказа. Возможен один актуальный PENDING. Будущая дата раньше текущего срока допустима.

Заказчик одобряет/отклоняет актуальный PENDING в тех же рабочих статусах. Одобрение меняет только текущий deadline; initial_deadline_at остаётся прежним. Отказ требует причины и сохраняет прежний срок. APPROVED, REJECTED и EXPIRED терминальны, повторное решение запрещено.

Актуальность требует будущей предложенной даты и совпадения previous_deadline_at с действующим сроком. GET показывает isCurrent=false для устаревшей заявки, не меняя БД. Перед созданием следующего запроса устаревший PENDING закрывается EXPIRED с TIME_EXPIRED/DEADLINE_CHANGED; некорректная новая команда не закрывает старую запись. Попытка решения по устаревшему PENDING фиксирует закрытие, событие/аудит/уведомление, коммитит их и возвращает 409 DEADLINE_REQUEST_EXPIRED. Повтор уже не повторяет эффекты. Фонового планировщика нет.

Сдача закрывает любой PENDING с ORDER_SUBMITTED в той же транзакции. После сдачи нельзя поздно согласовать новый срок. Приёмка закрывает оставшийся pending с ORDER_COMPLETED, если такой контекст сохранился. После доработки доступен новый самостоятельный запрос. Просрочка вычисляется сервером для активных заказов, не меняет статус и не запрещает допустимую сдачу/приёмку/доработку/изменение срока.

## Транзакции и события

OrderWorkService координирует транзакцию; SQL находится в OrderWorkRepository, обычное чтение соглашения/матрицы — в OrderRepository, работа с файлами — в FileService/FileRepository. Общий порядок блокировок: оба users по UUID → project → order → нужная version/request → файлы по UUID. После ожидания блокировки повторно проверяются роль/блокировка текущего участника, связи, статус, последняя версия и актуальность запроса. Заблокированная вторая сторона сама не действует, но не лишает действующего участника его собственных допустимых прав.

Контекст времени запроса срока рассчитывается по одному statement_timestamp PostgreSQL после получения блокировок. Создание/одобрение ещё раз проверяют предложенную дату по clock_timestamp в изменяющем SQL. Поэтому ожидание блокировок или прохождение даты не превращает устаревшую заявку в одобренную.

Создаются SUBMISSION_CREATED, REVISION_REQUESTED, ORDER_COMPLETED, DEADLINE_REQUESTED/APPROVED/REJECTED/EXPIRED с ссылкой на конкретную версию/заявку и относящимися к решению метаданными. В той же транзакции записываются audit_logs и уведомление второй стороне; автоматическое закрытие pending уведомляет исполнителя. В notifications решения по сроку имеют тип DEADLINE_DECIDED. Ошибка любого шага откатывает статусы, файлы, срок, решения, события, аудит и уведомления. UI аудита/уведомлений добавляется соответствующими поздними этапами.

## Интерфейс и проверка

В /orders/:id появились «Результаты работы» и «Изменение срока»: приватная история с пагинацией, новые сдачи с загрузкой/выбором свободных файлов, ссылки, замечания и подтверждение приёмки, запрос срока и подтверждение решения. Доступность кнопок приходит из серверных permissions, цель решения — конкретный UUID версии/заявки. Ошибка сохраняет введённые данные и показывается в соответствующем разделе. После успешной команды перечитываются заказ и обе истории. Если запись сохранилась, но обновление не удалось, интерфейс сообщает об этом и блокирует новые команды до обновления. Отмена формы оставляет новые uploads в личных свободных файлах.

`node scripts/test-infrastructure.mjs`: 73 unit-теста backend, 84 интеграционных теста PostgreSQL 17 и 6 тестов API-клиента — 163 всего. Новые проверки охватывают обе исходные договорённости, несколько версий и старые решения, приватные файлы, запрет подмены/редактирования, текущие роли/блокировки, просрочку, одобрение/отказ/истечение, стабильную пагинацию, гонки сдачи/решений/запросов и полный rollback при ошибке события. Отдельный тест меняет роль, пока команда ждёт блокировки user, и проверяет повторную авторизацию в транзакции.

Smoke через frontend proxy загружает приватный результат, согласует срок, закрывает pending при сдаче, возвращает первую версию на доработку, сдаёт вторую и принимает её. После реальной замены контейнеров проверяются обе версии, замечания, байты, решения по сроку и завершённые order/project. Тесты и браузерные сценарии используют отдельные Compose-проекты с целиком удаляемыми volumes; рабочие данные и неизменяемый аудит не очищаются обходом триггеров.

В браузере проверены обе стороны одного CLIENT в разных заказах: одобрение/отказ срока с причиной, запрос исполнителя с вводом будущей даты, загрузка TXT, серверная ошибка результата без файла/ссылки с сохранением комментария, сдача и закрытие pending, скачивание файла заказчиком, замечания, повторная сдача и приёмка только последней версии. Reload сохраняет результат и решения; на ширинах 390/1280 px горизонтального переполнения нет. Скриншоты сохранены вне Git, временные аккаунты/заказы/байты и скачанный тестовый файл удаляются после проверки.
