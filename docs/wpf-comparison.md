# Сравнение Workify с ООП-версией на WPF

Дата анализа: 20 октября 2026 года. Веб-версия: коммит `3a51929`, версия 1.0.0.

**Вывод:** основные пользовательские и административные сценарии WPF реализованы в веб-приложении. Полного функционального совпадения пока нет: отсутствует часть старых полей и команд, а управление проектами, заказами и рейтингом работает по другим правилам. При этом цикл выполнения заказа в веб-версии значительно подробнее.

В выделенных ниже 45 пунктах: **28 — полностью, 4 — частично, 8 — нет, 5 — изменено**. Это количество пунктов таблицы, а не процент готовности приложения: их объём и значимость различаются.

Основа сравнения — фактический код ООП-проекта из `_основа/курсовые/Объектно-ориентированное программирование/приложение` и текущего приложения из `приложение`. Проект по базам данных, старые спецификации и планы разработки не использовались как доказательство реализованной функции. Например, наличие процедур для модератора в старом SQL само по себе не означает наличие отдельного рабочего интерфейса модератора в ООП-версии.

Оценка «Полностью» означает, что пользовательское назначение функции обеспечено интерфейсом и серверной реализацией; она не означает совпадение всех технических деталей, форматов данных или доказанную безошибочность. Полный повтор сценариев в работающем приложении во время этого анализа не выполнялся: Docker Engine недоступен. Результаты проверок приведены ниже.

Обозначения:

- **Полностью** — основной сценарий WPF реализован; возможны дополнения веб-версии.
- **Частично** — есть основа или часть возможностей, но конкретные старые возможности отсутствуют.
- **Нет** — соответствующего действия или данных в текущем приложении нет.
- **Изменено** — вместо старого действия действует другая модель. Это различие в поведении, которое следует оценивать отдельно от незавершённой реализации.

Ссылки W ведут к старому коду, N — к текущему.

## Что появилось сверх старой WPF-версии

| Возможность | Фактическая реализация веб-версии |
|---|---|
| Полноценные отклики | Отдельная сущность, предложенная цена/срок/файлы, принятие, отклонение, отзыв отклика, история состояний |
| Заказ из двух источников | Общий механизм назначения из принятого отклика или приглашения; конкурентные принятия проверяются транзакционно |
| Согласованные условия | Условия и вложения сохраняются в контексте конкретного заказа; последующие заказы не подменяют его историю |
| Сдача результата | Нумерованные версии, комментарии, ссылки и приватные файлы |
| Доработки и приёмка | Заказчик возвращает версию с замечанием либо принимает результат; статус заказа меняется соответствующей командой |
| Запросы нового срока | Решение второй стороны, причины, история, проверки актуальности запроса |
| История событий | События создания, сдачи, доработок, сроков, завершения и отмены доступны в карточке |
| Повторное назначение | После отмены проект может получить новый заказ, сохранив старый и его данные |
| Публичные профили и раздельные рейтинги | Публичные портфолио и отзывы; рейтинги заказчика и исполнителя рассчитываются отдельно |
| Разбор жалобы в контексте работы | Администратор получает связанные данные заказа, решений, сроков, версий и отзывов |
| Санкции | Предупреждения, временные/постоянные блокировки и история мер; действия пишутся в аудит |
| Веб-инфраструктура | React, Express API, PostgreSQL, Docker Compose, миграции, локальное файловое хранилище, проверка доступности сервисов |
| Проверки | Unit, интеграционные и HTTP E2E-сценарии; проверка миграций, ограничений и сохранности данных при замене контейнеров |

Основание: [N-proposals], [N-invitations], [N-assignment], [N-order-work], [N-course-e2e], [N-admin], [N-tests].

Платежей, email/push, чата и отдельной инфраструктуры MinIO/Redis в текущем курсовом нет. В изученном рабочем интерфейсе ООП/WPF нет основания считать их уже реализованными функциями, которые потерялись при переносе. Упоминания таких возможностей в более широких спецификациях следует сравнивать с реализацией отдельно.

## Что доработать, если требуется функциональное совпадение с WPF

1. Добавить смену собственного пароля: сейчас отсутствует и форма, и серверная команда.
2. Определить, нужны ли старые CRUD-действия администратора. Сейчас административное управление пользователями реализовано как просмотр и санкции; создание, изменение чужих данных/пароля, удаление и произвольное назначение роли не перенесены.
3. Добавить отсутствующие данные: отчество/пол профиля, опыт и навыки конкретной работы портфолио, изображение или вложения отзыва.
4. Решить правила редактирования/удаления поданной жалобы. В WPF эти команды были, в веб-версии поданная жалоба неизменяема для автора.
5. При необходимости восстановить экспорт/импорт аудита, языки RU/EN, переключение темы и обновление последнего присутствия.
6. Проверить, требуется ли поддержка GIF/BMP. Сейчас набор поддерживаемых файлов другой.

Удаление заказа, произвольная установка его статуса, широкая публичная видимость проектов, ручная правка рейтинга и физический перенос в архив не следует автоматически считать недописанными функциями: у веб-приложения для них уже существует другая модель. Перед возвратом старого поведения потребуется согласовать именно бизнес-правила.
