# Файлы, аватар и портфолио Workify

Этап 07 использует общий FileService, Multer 2.4.0, определение сигнатуры через file-type 22.2.0 и LocalStorage. Физические объекты находятся в существующем volume uploads_data, смонтированном в /app/uploads. PostgreSQL хранит только метаданные stored_files и связи profile_files/portfolio_files. Миграция 004 добавляет SHA-256 и отметку отложенного удаления, сохраняя старые записи и их идентификаторы.

## API

Защищённые операции используют Bearer JWT, действующую сессию и актуальную роль CLIENT. Владелец берётся из сессии; произвольные userId, uploadedBy, storageKey, MIME и размер в JSON не принимаются.

| Метод и путь | Назначение / ответ |
|---|---|
| POST /api/files | Один multipart-файл в поле file, без текстовых полей; 201 `{file}` |
| GET /api/files | Метаданные своих файлов, включая inUse; `{files}` |
| GET /api/files/:fileId | Поток после проверки доступа; UUID вместо физического пути |
| DELETE /api/files/:fileId | Удаление своего свободного файла; 204 |
| GET /api/me/avatar | `{avatarFileId}` или null |
| PUT /api/me/avatar | `{fileId}` — назначение собственного изображения; `{avatarFileId}` |
| DELETE /api/me/avatar | Удаление текущего аватара; 204 |
| GET /api/me/portfolio | Свои работы; `{items}` |
| GET /api/me/portfolio/:itemId | Своя работа; `{item}` |
| POST /api/me/portfolio | Создание; 201 `{item}` |
| PUT /api/me/portfolio/:itemId | Полная замена редактируемых полей и вложений; `{item}` |
| DELETE /api/me/portfolio/:itemId | Удаление своей работы и её вложений; 204 |
| GET /api/users/:userId/portfolio | Публичные работы активного CLIENT; `{items}` |

Метаданные файла: id, originalName, mimeType, sizeBytes, sha256, createdAt. Физический ключ и uploaded_by не выдаются. Поля работы: id, title, description, links, files, createdAt, updatedAt. Название — 1–200, описание — 1–5000 символов; допустимы переносы строк, но не NUL/управляющие символы. До пяти полных http/https ссылок без credentials, до восьми уникальных UUID вложений. Пропущенные links/fileIds в PUT означают пустые списки. В текущей модели навыки задаются на уровне профиля; отдельного справочника навыков работы не требуется.

## Ограничения и права

Разрешены PNG, JPEG, WebP, PDF, UTF-8 TXT, DOCX, ZIP и MP4, каждый до 10 МиБ. Проверяются исходное имя, расширение, заявленный MIME и сигнатура содержимого. Для TXT дополнительно проверяются UTF-8 и отсутствие бинарных управляющих символов. Нулевой размер, SVG/HTML/исполняемые форматы, подмена расширения, пути, лишние multipart-поля/файлы отклоняются. Исходное имя сохраняется только как метаданные; на диске используется UUID с проверенным расширением. LocalStorage разрешает только basename внутри uploadDir, создаёт файл эксклюзивно с правами 0600 и не открывает symlink.

Multer подключён только к POST /files после авторизации. В памяти одновременно не более четырёх загрузок по 10 МиБ на процесс. Записи ограничены 50 файлами и 30 работами на CLIENT; изменения файлов и портфолио ограничены каждые своим общим лимитом 60/15 минут на IP. Как и у auth, текущий frontend proxy объединяет браузеры под своим IP. Multipart имеет тайм-аут клиента 60 секунд, proxy — 60/65 секунд. Слишком большой файл возвращает 413, неподдерживаемый тип — 415, ошибки формы/полей — 400/422, превышение квоты — 409, лимита запросов — 429.

Свободная загрузка доступна только владельцу, включая скачивание с Bearer JWT. Файл становится публичным после привязки к аватару/портфолио активного CLIENT или его OPEN-проекту. Для [проектов этапа 08](projects.md) файлы черновиков и остальных статусов доступны владельцу; блокировка/переход в ADMIN скрывает публикацию. [Принятие отклика](proposals.md) сохраняет связи в order_files: обе стороны заказа с действующей сессией могут читать эти файлы и после закрытия публичного проекта. Публичность вычисляется по связям и v_public_profiles при каждом скачивании. Неизвестный и чужой закрытый файл имеют одинаковый 404. ADMIN не получает произвольный доступ к чужим загрузкам.

Привязать можно только свой свободный файл, сохраняя уже прикреплённые файлы при редактировании той же работы или проекта. Один файл не переиспользуется в разных сущностях: для этого загружается отдельная копия. Прямое удаление используемого файла возвращает 409; проверяются все шесть существующих таблиц связей, включая будущие private-контексты. Для замены аватара принимаются только JPEG/PNG/WebP. Анонимная выдача не использует cookie авторизации. Весь uploads volume по HTTP не раздаётся.

Поток содержит no-store, nosniff, ограничивающую CSP и безопасный Content-Disposition с исходным именем. Растровые изображения выдаются inline, остальные форматы — attachment. React выводит текст без исполнения HTML; внешние ссылки используют noopener/noreferrer. Свободные файлы скачиваются интерфейсом через авторизованный Blob-запрос с одним повтором после refresh.

## Транзакции и физическое удаление

Все изменения одного владельца сериализуются блокировкой users, затем при необходимости блокируются файлы. Права и актуальная блокировка проверяются повторно внутри транзакции. Чужой/несуществующий UUID отклоняет всю операцию; конкурентная привязка одного файла имеет одного победителя. Контроллеры не содержат SQL и бизнес-правил; repositories работают через один pg client транзакции. Только LocalStorage использует файловую систему.

При загрузке FileService проверяет квоту, сохраняет объект, затем вставляет метаданные. Ошибка записи/транзакции вызывает очистку нового объекта. Перед удалением связи меняются в транзакции, а для свободных объектов фиксируется deleted_at. Такие файлы сразу недоступны через API. После commit удаляются байты, затем метаданные. ENOENT считается успешной повторной очисткой. При сбое диска/БД отметка остаётся; обработчик повторяется при старте и раз в минуту, по 100 записей за проход. Логи не содержат имён, физических путей, содержимого или SQL.

Файловая система и PostgreSQL не имеют общей транзакции. Аварийное завершение процесса между сохранением нового объекта и commit либо неуспешная компенсирующая очистка может оставить физический объект без метаданных. Автоматического сканирования/удаления таких объектов нет; это задача обслуживания и сверки резервных копий. Они не доступны через API. Антивирус, полная проверка структуры медиа, безопасная распаковка, thumbnails, S3 и Range-видео в этот этап не входят. Проверка сигнатуры не является антивирусом; архивы не распаковываются сервером. Существующие записи до 004 могут иметь sha256=null; для каждой новой загрузки вычисляется digest.

## Интерфейс и проверки

В /me/profile добавлены аватар и портфолио: создание/редактирование/отмена, ссылки, загрузки, выбор ранее загруженных свободных файлов, удаление с подтверждением в карточке. Удалённые из черновика старые вложения очищаются только после сохранения. Отмена оставляет новые загрузки в разделе «Свободные файлы», где их можно повторно прикрепить или удалить. /users/:id показывает сохранённые работы и вложения гостям. Ошибки API оставляют черновик доступным для исправления.

`node scripts/test-database.mjs` проверяет четыре миграции, повторное применение, ограничения, rollback и конкуренцию на временном PostgreSQL 17. `node scripts/test-infrastructure.mjs` собирает отдельный Compose: 83 unit-теста backend, 119 интеграционных тестов и 6 тестов API-клиента. Включены подмена типа, размер, traversal/symlink, приватные загрузки, чужие UUID, CRUD, безопасные ссылки, повторная привязка, аватар, блокировки, откат метаданных и повтор физического удаления. Проверяются снимки файлов принятого отклика/приглашения, доступ из [карточки заказа](orders.md) и сохранность при изменении проекта. Smoke действительно заменяет контейнеры и проверяет прежние байты, метаданные и связи портфолио/проекта/заказа, включая доступ исполнителя к закрытому снимку. Рабочие volumes при автоматических тестах не используются.

В браузере проверены загрузка тестового PNG и TXT, сохранение/отмена/reload, гостевой просмотр и отсутствие горизонтального переполнения при ширине 390 px. Временный QA-аккаунт и его файлы удаляются после проверки.

Источники поведения: ООП PortfolioViewModel.cs и UserPortfolioRepository.cs, текущая спецификация 08_rest_api.md, 10_media_storage.md и 12_security.md. CRUD, описание и вложения адаптированы к текущим title/description/links и таблицам связей; WPF/EF, Base64 и хранение бинарников в БД не переносятся. API Multer сверено с [официальной документацией Express](https://expressjs.com/en/resources/middleware/multer/), определение сигнатуры — с [file-type](https://github.com/sindresorhus/file-type).
