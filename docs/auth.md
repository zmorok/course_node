# Регистрация, вход и роли Workify

Этап 05 добавляет регистрацию, вход, текущего пользователя, выход и восстановление сессии в React. Системные роли — `CLIENT` и `ADMIN`. Заказчик и исполнитель остаются режимами одного CLIENT. [Управление своим профилем](profile.md) добавлено на этапе 06; проекты и администрирование пользователей относятся к следующим этапам.

## API

| Метод и путь | Доступ | Результат |
|---|---|---|
| POST /api/auth/register | Гость | 201, `{user, accessToken}` и refresh-cookie |
| POST /api/auth/login | Гость | 200, `{user, accessToken}` и новая сессия |
| POST /api/auth/refresh | Refresh-cookie | 200, `{user, accessToken}` и новая refresh-cookie |
| POST /api/auth/logout | Refresh-cookie, включая заблокированный аккаунт | 204, отзыв текущей сессии и очистка cookie |
| GET /api/auth/me | Bearer JWT и действующая сессия | 200, `{user}` |
| GET /api/admin/access | Bearer JWT, действующая сессия и ADMIN | 200, `{user, access: "ADMIN"}` |

Все POST требуют `X-Workify-Client: browser`; cross-site запросы с `Sec-Fetch-Site: cross-site` отклоняются. Login/register принимают JSON. CORS не включён: frontend обращается к `/api` своего origin через proxy. Дополнительный заголовок требует browser preflight при обращении с чужого origin; в сочетании с SameSite-cookie это защищает cookie-операции, включая login CSRF.

Регистрация принимает только `email`, `username`, `password`, `firstName`, `lastName`. Email ограничен 254 символами, username — 3–40 символами латиницы/цифр/подчёркивания, имена — 1–100. Пароль — 12–128 символов; не обрезается и не нормализуется. Клиент повторяет пароль в форме; `confirmPassword` не отправляется в API. Все ограничения повторно проверяются backend. Поля role/status/id и любые неизвестные поля отклоняются с 422. Role CLIENT устанавливает SQL сервера. В одной транзакции создаются users, profiles и сессия.

Email и username уникальны без учёта регистра. Дубликат возвращает 409 ACCOUNT_EXISTS. Login принимает email и пароль; неверный пароль и неизвестный email дают одинаковый 401 INVALID_CREDENTIALS, включая проверку dummy hash для неизвестного email. Публичный user содержит только id/email/username/role/effective status/firstName/lastName. Пароль и его hash не входят в ответы. Ошибки используют [общий формат](backend.md#формат-ошибок).

## Сессии и защита доступа

Пароли хешируются Argon2id: memory=19456 KiB, time=2, parallelism=1, уникальная случайная соль в каждом hash. Access JWT подписывается `jose` с HS256: проверяются подпись, алгоритм, typ, issuer, audience, sub/sid, exp/iat/jti и максимальный возраст. По умолчанию JWT действует 15 минут; роль не переносится в доверенные claims.

Refresh token — 32 случайных байта, закодированных base64url. Браузер получает host-only cookie `workify_refresh` с HttpOnly, SameSite=Strict и Path=/api/auth. В БД находится только SHA-256 digest случайного токена. JWT хранится в памяти JS, не в localStorage/sessionStorage и не в cookie. Refresh token не возвращается в JSON.

[Миграция 003](../database/migrations/003_auth_sessions.sql) добавляет auth_sessions и auth_refresh_tokens, сохраняя прежнюю схему. Сессия имеет абсолютный срок 30 дней: refresh его не продлевает. Каждый refresh потребляет текущий token и выдаёт новый в той же транзакции. Старая запись сохраняется для обнаружения replay. Повтор использованного token отзывает всю сессию; отзыв коммитится до возврата 401. Операции сериализуются блокировкой строки сессии; consumed_at перечитывается отдельным запросом после получения lock, чтобы видеть результат конкурирующего refresh.

`authMiddleware` проверяет JWT и каждый раз читает действующую сессию и пользователя из PostgreSQL. Logout немедленно блокирует все access JWT этой сессии, даже до их exp. Другие сессии аккаунта остаются действующими. Отсутствующая/истёкшая/отозванная сессия даёт 401; действующая блокировка — 403 ACCOUNT_BLOCKED. Login проверяет блокировку после пароля. Refresh заблокированного аккаунта отзывает текущую сессию. Временная блокировка перестаёт ограничивать доступ после blocked_until; это эффективный статус в ответе, исторические поля блокировки не переписываются.

`roleMiddleware('ADMIN')` применяется после authMiddleware. Поэтому смена роли или блокировка действует и для уже выданного JWT; скрытие кнопок React не является проверкой прав. `/api/admin/access` подтверждает доступ, не предоставляет CRUD будущей admin-панели.

Refresh/logout не требуют access JWT: cookie достаточно, поэтому выход доступен и после истечения JWT или блокировки. Повторный logout без cookie возвращает 204. Ошибки refresh 401/403 очищают cookie; технические 5xx сохраняют её для повторной попытки. Все auth-ответы используют Cache-Control: no-store.

## React

На старте страницы клиент выполняет refresh и восстанавливает user. В пределах вкладки используется single-flight Promise, между вкладками — Web Locks, чтобы штатные параллельные запросы не выглядели как replay. В браузерах без Web Locks сохраняется защита одной вкладки; конкурирующий refresh в нескольких вкладках может потребовать повторного входа. Выход рассылается другим вкладкам через BroadcastChannel.

При 401 защищённого запроса API-клиент обновляет сессию и повторяет запрос один раз. При 401/403 refresh или ACCOUNT_BLOCKED локальный user сбрасывается. При сетевой ошибке восстановления доступна повторная попытка. При ошибке выхода форма показывает проблему, сохраняя текущий user до подтверждённого ответа сервера. Формы имеют подписи, autocomplete, отображение ошибок полей, подтверждение пароля и блокировку повторной отправки.

## Конфигурация и первый ADMIN

```powershell
node scripts/setup-env.mjs
docker compose up --build -d --wait
```

setup-env создаёт случайные секреты БД/JWT. Если старый .env уже существует и AUTH_JWT_SECRET отсутствует, скрипт только дописывает новый секрет, сохраняя остальные настройки. Значения секретов не выводятся. Образ backend устанавливает закреплённые версии argon2/jose/helmet/express-rate-limit через npm ci; тесты выполняются на Node.js 24 Alpine с нативным Argon2.

| Переменная | Значение | Проверка |
|---|---|---|
| AUTH_JWT_SECRET | Обязательные 32 случайных байта в hex | 64 hex-символа; повтор одного символа запрещён |
| AUTH_ACCESS_TTL_SECONDS | 900 | 60–3600 |
| AUTH_SESSION_TTL_DAYS | 30 | 1–90 |
| AUTH_COOKIE_SECURE | false для локального HTTP | Только true/false; true для deployment через HTTPS |

JWT secret должен сохраняться между пересозданиями контейнера. Его замена делает старые JWT недействительными; действующая refresh-сессия может выдать новый JWT. Пример .env не содержит рабочего ключа.

Демонстрационных пользователей и общих admin-паролей нет. Для первого администратора зарегистрируйте обычный аккаунт и выполните доверенную операторскую команду в контейнере:

```powershell
docker compose exec -T backend node src/commands/promote-admin.js your-email@example.com
```

Команда повышает только существующий аккаунт; не вызывается автоматически и не доступна через HTTP. Это операция владельца локального deployment с доступом к Docker. Обновите данные аккаунта в интерфейсе; повторный вход для применения роли не нужен. В тестах команда применяется только к временной тестовой записи.

Helmet устанавливает заголовки безопасности API. Login/register делят лимит 20 попыток за 15 минут на IP, refresh/logout — 120. Лимиты возвращают общий JSON 429 и Retry-After. trust proxy выключен, входным X-Forwarded-For не доверяем. В текущем Compose proxy объединяет запросы браузеров под своим IP; это консервативный общий лимит для локального запуска. Memory store рассчитан на один backend, очищается при перезапуске. Письма подтверждения, восстановление пароля, MFA и автоматическая очистка истёкших сессий в этот этап не входят.

## Проверки и источники

```powershell
node scripts/test-database.mjs
node scripts/test-infrastructure.mjs
```

Проверки авторизации входят в общий набор: 49 unit-проверок backend, 27 интеграционных тестов PostgreSQL 17 и 4 теста API-клиента. Для auth проверяются Argon2id/соли/пробелы, JWT с неверной подписью/алгоритмом/audience/сроком, регистрация, дубликаты, CLIENT/ADMIN, смена роли для прежнего JWT, блокировки, ротация/replay, конкурирующий refresh, logout, CSRF/rate limit. Runner также проверяет auth через frontend proxy, операторскую команду ADMIN, восстановление сессии после замены контейнеров и отзыв JWT при выходе. Все автоматические фикстуры создаются в одноразовых базах; [профильные проверки и исправление повтора 403](profile.md) добавлены на этапе 06.

Ручная проверка в браузере: несовпадение паролей, регистрация, неверный/правильный login, восстановление после reload, обновление роли, admin-доступ, выход с синхронизацией двух вкладок и узкая ширина панели. Собственная браузерная тестовая запись удаляется после проверки.

Из исторической базы прочитаны OOP `FreelanceApp/Authentication/LoginWindow.xaml.cs`, `RegisterWindow.xaml.cs` и `Windows/ViewModels/Admin/UserManagmentViewModel.cs`. Сохранены email-вход, обязательные имя/фамилия и серверный выбор клиентской роли; SHA-512, показ пароля после регистрации и прямой доступ desktop-клиента к БД не переносятся. Сопоставлены текущие `_материалы/Workify_STSR_Project_Specification_v4/docs/08_rest_api.md` и `12_security.md`; путь API взят из stage prompt (/api), платежи исключены.

Первичные источники: [node-argon2](https://github.com/ranisalt/node-argon2), [jose](https://github.com/panva/jose), [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
