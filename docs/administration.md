# Административная панель

Этап 16 добавляет /admin/users и /admin/complaints. Все административные API требуют действующую сессию ADMIN; CLIENT и заблокированные/пониженные администраторы доступа не получают. Права повторно проверяются внутри изменяющей транзакции. Пароли, хеши, refresh credentials и storage keys в DTO не включены. Редактирования ролей, паролей и профилей через панель нет. Схема из четырёх миграций используется без изменений.

## Пользователи и ограничения

GET /api/admin/users принимает search (буквальный поиск имени, логина или email до 100 символов), role=CLIENT/ADMIN, status=ACTIVE/BLOCKED, sort=newest/name и page/pageSize. Истёкшая временная блокировка считается неактивной при фильтрации. Порядок имеет UUID как последний ключ; total сохраняется за последней страницей. GET /api/admin/users/:userId возвращает контактные данные, фактическое состояние, рейтинги, первые страницы санкций и жалоб с участием пользователя. GET /api/admin/users/:userId/sanctions пагинирует полную историю. Жалобы доступны с userId-фильтром общей очереди.

POST /api/admin/users/:userId/block принимает только type=TEMPORARY_BLOCK/PERMANENT_BLOCK, reason (1–5000) и expiresAt (для временной обязателен будущий ISO с часовым поясом, для постоянной null). POST /api/admin/users/:userId/unblock принимает только обязательный reason. Получатель должен оставаться CLIENT; ADMIN и сам администратор не блокируются. Отдельное предупреждение выдаётся [командой этапа 15](complaints-and-warnings.md).

Блокировки сериализуются строками ADMIN и клиента по UUID. Каждая мера сохраняет moderation_action, аудит и постоянное уведомление; сессии блокируемого клиента отзываются. Текущий запрет не ослабляется короткой новой мерой: постоянный сохраняет силу, временный сохраняет максимальный срок. Более строгая мера обновляет состояние аккаунта. Разблокировка очищает запрет, сохраняет last_unblocked_at и USER_UNBLOCKED с причиной; повтор не создаёт второй аудит. История append-only не изменяется, предупреждения не отзываются. Старые блокировки до last_unblocked_at не возобновляются при новой мере. Заказы и проекты не переводятся в другой статус из-за санкции; после разблокировки отозванная сессия требует нового входа.

## Очередь и полный контекст

GET /api/admin/complaints поддерживает id, status, reporter/target (часть логина), orderId, projectId, categoryId, reason, userId (любая сторона), assignedAdminId, assignment=all/mine/unassigned, createdFrom/createdTo и пагинацию. Даты нормализуются в ISO, обратный интервал отклоняется. Порядок created_at, id ставит старые обращения первыми. Неизвестные фильтры отклоняются. Общие границы: page 1–10000, pageSize 1–24, по умолчанию 1/12; ответы no-store.

GET /api/admin/complaints/:complaintId показывает текст, доказательства, заявителя/адресата, обработчика, даты и итог. Order содержит исходный снимок задания/файлов, цену, первоначальный и текущий срок, завершение либо причину/автора отмены, принятый отклик или приглашение. Текущее состояние проекта показано отдельно от исходного соглашения. Обе стороны ведут к административным карточкам с прежними жалобами, санкциями и рейтингами.

GET /api/admin/complaints/:complaintId/submissions, /deadline-requests, /events и /reviews независимо пагинируют версии с комментариями/решениями/файлами, согласование срока, временную шкалу и отзывы, включая скрытые автором. Вкладки привязывают загруженные данные к пути запроса: при переключении прежний формат данных не используется в новом разделе. Загрузка, пустые состояния, ошибки и повтор предусмотрены.

FileService разрешает действующему ADMIN читать доказательства жалоб и связанные файлы проекта, соглашения и сдач. Произвольные свободные загрузки клиентов не открываются. Проверка ADMIN выполняется также в SQL выдачи файла; понижение роли сразу убирает специальный доступ. Клиентские правила и приватность для новой стороны переназначенного проекта сохраняются.

## Решение по жалобе

POST /api/admin/complaints/:complaintId/claim с пустым body переводит только NEW → IN_REVIEW, фиксируя ADMIN/claimed_at, аудит и уведомление заявителю. Два claim имеют одного победителя; перехвата и переназначения нет.

POST .../reject принимает resolutionNote (1–5000), переводит назначенную жалобу IN_REVIEW → REJECTED, записывает отдельный REJECT moderation action без получателя и санкций. POST .../resolve принимает resolutionNote и actions: от 1 до 6 уникальных пар targetId/type. Каждый action содержит targetId, type=WARNING/TEMPORARY_BLOCK/PERMANENT_BLOCK, обязательный reason и допустимый expiresAt. Целями могут быть только первоначальные стороны заказа с текущей ролью CLIENT. Разрешены разные меры обеим сторонам и разные типы мер одной стороне; повтор одного типа для одной стороны отклоняется. Произвольные status/adminId, третьи лица, пустые причины и неправильные сроки запрещены.

Порядок блокировок: users по UUID (ADMIN и обе стороны) → project → order → complaint. Обработчик и IN_REVIEW проверяются под блокировкой. Санкции, связанные warnings, отзыв сессий/состояние аккаунтов, RESOLVED/resolutionNote, аудит и уведомления фиксируются одной транзакцией. Ошибка любого шага откатывает всё, включая уже применённую меру первой стороне. Повторное решение, другой ADMIN и решение до claim получают 409. Историческая жалоба и её стороны не меняются после нового назначения проекта.

## Проверки и источники

`node scripts/test-infrastructure.mjs`: 83 unit-теста backend, 119 интеграционных тестов PostgreSQL 17 и 6 тестов API-клиента — 208 всего. Проверены поиск/буквальные спецсимволы, фильтры и пагинация, ADMIN/CLIENT/блокировки, оба источника, исходные файлы и приватные доказательства, версии/сроки/события/скрытый отзыв после нового назначения, конкурентный claim, только назначенный обработчик, REJECT без санкций, меры обеим сторонам, истечение/строгость/разблокировка, неизменяемая история, отзыв JWT, полный rollback позднего аудита и свежая проверка ADMIN после ожидания блокировки.

Smoke проходит claim и resolve с привязанным предупреждением через frontend proxy; после пересоздания контейнеров проверяются итог жалобы, доказательства и обе записи предупреждений. Браузерная проверка выполняется в отдельном временном окружении: очереди/детали, скачивание доказательства, переключение всех разделов контекста, разные санкции сторонам, отказ с сохранением обоснования, отклонение, пользовательские меры, история и адаптивность.

Изучены прежние UserManagmentViewModel.cs, AdminUsersRepository.cs, ComplaintsModerationViewModel.cs и AdminModerationRepository.cs; сопоставлены актуальные 18_admin_complaint_logic.md, [предметная модель](domain-model.md) и [переходы](state-transitions.md). Сохранён административный разбор с контекстом; старый произвольный CRUD аккаунтов, смена ролей/паролей, WPF/EF и раздельные неатомарные выдача предупреждения/закрытие жалобы не перенесены.
